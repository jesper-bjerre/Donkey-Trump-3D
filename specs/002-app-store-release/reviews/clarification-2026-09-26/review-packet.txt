3: ## Core Principles
4: 
5: ### I. Native iPhone Play Comes First
6: 
7: The product MUST remain a native 3D arcade game with iPhone as its primary acceptance target.
8: Starting, restarting and playing installed game content MUST work without a backend connection.
9: Optional online features MUST load asynchronously, have finite user-visible deadlines, and leave
10: navigation usable while loading or failing. A late response MUST NOT interrupt a newer game or
11: change a different run's result. Network or storage work MUST NOT block the render loop or UI thread.
12: 
13: New or changed player-facing screens MUST work in landscape with safe areas, readable text and
14: reachable actions. Applicable menu/list controls MUST support VoiceOver and larger text. Changes
15: MUST preserve the existing Reduce Motion, sound and haptics settings unless the feature explicitly
16: changes their behaviour. These rules keep short play sessions usable on the baseline iPhone.
17: 
18: ### II. Simple Components and Explicit Ownership
19: 
20: Gameplay rules, scoring, collision logic and run transitions MUST remain testable independently of
21: SceneKit, SwiftUI and networking. Rendering presents simulation state; UI presents player actions
22: and results. Cross-thread state transfers MUST use snapshots or an explicit synchronization boundary;
23: new UI state MUST have a defined main-thread/main-actor owner.
24: 
25: The backend default is one small ASP.NET Core service in `src/backend`, using built-in platform
26: facilities and a separate test project when needed. Additional services, stores, frameworks or
27: architectural layers MUST have a feature-level justification explaining the requirement they solve
28: and why the existing structure is insufficient. Package versions and runtime baselines belong in
29: project files and feature plans, rather than being frozen permanently in this constitution.
30: 
31: Each state has a clear owner: the app owns local gameplay and its personal best; the backend owns
32: validation, ordering and persistence of shared rankings. Accepting a client-reported score MUST NOT
33: be described as proof of genuine gameplay. Simplicity does not remove these ownership boundaries.
34: 
35: ### III. Correct Shared Data and Bounded Failures
36: 
37: Shared read-modify-write state MUST use storage-enforced concurrency control that works across
38: multiple service instances. An in-process lock alone is insufficient. A conflict retry MUST read
39: current state and recompute the result; unconditional overwrite MUST NOT be a fallback. Duplicate
40: submissions MUST use a stable result identity, with the supported deduplication scope documented.
41: 
42: Remote operations MUST define deadlines, cancellation behaviour, retry conditions and finite retry
43: limits. A potentially committed write with a lost acknowledgement MUST be reported as unconfirmed;
44: retry behaviour MUST NOT imply that a failed response proves no save occurred. Missing, corrupt or
45: unavailable storage MUST NOT silently become an empty replacement. Tests MUST cover these distinctions
46: when shared persistence is introduced or changed.
47: 
48: Local personal-best data MUST survive remote failures. Cached results MUST be identifiable as stale
49: and MUST NOT establish fresh qualification or confirmed publication. For the agreed highscore v1,
50: a failed qualification or submission MUST NOT create an automatic, deferred or next-launch upload.
51: 
52: ### IV. Original Content and Deliberate Data Use
53: 
54: Game models, textures, animation and audio MUST remain original project material or have documented
55: permission compatible with their use. Copied Nintendo/Donkey Kong assets MUST NOT replace the
56: project's procedural characters or synthesized soundtrack. References to the original game's feel
57: are design inspiration, not authorization to copy its assets. Player copy MUST preserve the original
58: parody/no-affiliation description.
59: 
60: Public name/score publication MUST require an explicit player action and explain what is public.
61: Data collection and logs MUST be limited to the feature's documented purpose; diagnostics MUST NOT
62: record secrets, full submission bodies or player names. Storage credentials MUST stay out of the
63: app, repository and logs. Public service traffic MUST use HTTPS; local development exceptions MUST
64: remain isolated from release configuration. Azure-hosted storage access MUST use managed identity
65: with permissions scoped to the required data resources.
66: 
67: Privacy/help copy MUST match implemented data flows. A new account, analytics, advertising or
68: tracking capability MUST be an explicit product-scope change, never an incidental dependency.
69: 
70: ### V. Evidence Before Completion Claims
71: 
72: Changed gameplay rules, persistence, concurrency, retry and cancellation behaviour MUST have
73: repeatable checks for their observable outcomes and relevant failure cases. Use deterministic
74: inputs, clocks or service/storage substitutes where timing and randomness would hide defects.
75: Cross-component contracts MUST be checked at their boundaries; a test that only mirrors an
76: implementation detail is not sufficient evidence for the player's requirement.
77: 
78: Verification MUST be proportional to the change. Run the affected build/tests and relevant existing
79: regression checks; documentation-only edits need document validation, not an unrelated full build.
80: Device-dependent claims, including physical silent-switch behaviour, touch usability and sustained
81: performance, MUST be backed by checks on the relevant physical device before release acceptance.
82: A simulator pass MUST NOT be presented as physical-device evidence.
83: 
84: Reports and documentation MUST distinguish planned, implemented, tested and deployed behaviour,
85: identify what was actually checked, and record material limitations. Test instructions or a scaffold
86: MUST NOT be reported as a passing feature. Historical results MUST retain their date/context rather
87: than silently becoming evidence for a newer build.

### FILE specs/001-global-highscores/spec.md
1: # Feature Specification: Global Top 100 Highscores
2: 
3: **Feature Branch**: `main` (existing branch; no feature branch created)
4: 
5: **Feature Directory**: `specs/001-global-highscores`
6: 
7: **Created**: 2026-09-26
8: 
9: **Status**: Implemented and locally validated; see [validation.md](validation.md). Physical-device, container and live Azure release checks remain pending. No deployment or release claim.
10: 
11: **Input**: The iPhone game needs a shared top-100 highscore list. After Game Over, qualifying players enter a name and see their score centred in the list. Non-qualifying players see the bottom. The list is also available from the title screen and must never delay starting a game. Scores must survive service restarts and simultaneous submissions. Keep the solution simple and inexpensive.
12: 
13: ## User Scenarios & Testing *(mandatory)*
14: 
15: ### User Story 1 - Publish a qualifying result (Priority: P1)
16: 
17: After losing my last life, I want to enter a name for a qualifying score and see my position among other players, so my achievement feels recognised.
18: 
19: **Why this priority**: A persistent shared ranking is the main value of the feature.
20: 
21: **Independent Test**: Complete a run against a prepared list with a known cutoff. Submit a qualifying result, verify its highlighted position, and reopen the list from another installation to confirm it was saved.
22: 
23: **Acceptance Scenarios**:
24: 
25: 1. **Given** fewer than 100 saved results, **When** a run ends with a valid score, **Then** the player is invited to enter a name, including when the score is zero.
26: 2. **Given** a full list, **When** a completed run scores more than rank 100, **Then** the player is invited to enter a name and sees that the name and score will be public.
27: 3. **Given** a qualifying run and a valid name, **When** submission succeeds, **Then** the player sees the saved list with their entry highlighted and vertically centred. Near either end, use the nearest available position keeping the whole row visible.
28: 4. **Given** a name prompt, **When** the player cancels, **Then** nothing is submitted and Play Again and Return to Title remain available.
29: 5. **Given** an empty, whitespace-only, multiline, control-character or over-20-character name, **When** submission is attempted, **Then** an inline explanation appears and nothing is published until the name is valid.
30: 6. **Given** the list changes while a name is entered, **When** the score no longer qualifies at save time, **Then** no success is claimed and the updated bottom of the list is shown with an explanation.
31: 7. **Given** a submitted entry remains ranked, **When** the identical submission is repeated, **Then** it has one entry and retains its original tie position; changing its name or score under the same run identity is rejected.
32: 
33: ### User Story 2 - See the next target after missing the list (Priority: P1)
34: 
35: After a run that does not reach the top 100, I want to see the lowest listed scores and my own result, so I know what to aim for next.
36: 
37: **Why this priority**: This completes the end-of-run experience for most players and encourages another attempt.
38: 
39: **Independent Test**: Complete runs below and exactly at the cutoff in a prepared full list; confirm there is no name prompt and rank 100 is visible.
40: 
41: **Acceptance Scenarios**:
42: 
43: 1. **Given** 100 results and a score below rank 100, **When** qualification is checked after Game Over, **Then** the bottom opens with rank 100 visible, the final score remains visible, and no name is requested.
44: 2. **Given** a full list and a score equal to the cutoff, **When** qualification is checked, **Then** the previously saved equal score keeps its place and the new run does not qualify.
45: 3. **Given** the result list, **When** Play Again or Return to Title is selected, **Then** that action proceeds without waiting for another highscore operation.
46: 
47: ### User Story 3 - Browse from the title without delaying play (Priority: P1)
48: 
49: I want to open Highscores from the title screen while always being able to start playing, even when the shared service is slow or unavailable.
50: 
51: **Why this priority**: The online feature must preserve the game's immediate, offline-capable start.
52: 
53: **Independent Test**: Launch with a service that responds normally, responds late, and never responds. Start a game during each condition and inspect list loading/error states independently.
54: 
55: **Acceptance Scenarios**:
56: 
57: 1. **Given** the title screen, **When** Highscores is selected, **Then** the list opens from the top with rank, name and score and clear loading, empty and unavailable states.
58: 2. **Given** a background list load is pending or failed, **When** Start Game is selected, **Then** the normal intro/game flow begins immediately, with no network gate or disabled Start button.
59: 3. **Given** a list view is loading, **When** the player closes it and starts a run, **Then** a late response cannot reopen the list, show a name prompt or interrupt the run.
60: 4. **Given** an unavailable service, **When** Highscores is opened, **Then** loading ends within eight seconds with a readable error and a list-refresh action; the list can always be closed.
61: 5. **Given** a list loaded earlier in this app session, **When** refresh fails, **Then** those entries may remain visible only with a clear indication that they may be out of date. They cannot establish current qualification.
62: 6. **Given** larger text or VoiceOver on an iPhone in landscape, **When** the list is opened, **Then** rank, name and score can be read, navigation remains reachable, and the highlighted row is not hidden by the keyboard or screen edges.
63: 
64: ### User Story 4 - Preserve the ranking during simultaneous submissions (Priority: P1)
65: 
66: As a player, I want simultaneous results evaluated together so another player's submission cannot accidentally erase mine.
67: 
68: **Why this priority**: A shared highscore list needs consistent ranking across devices.
69: 
70: **Independent Test**: Submit many distinct prepared results concurrently, then compare the saved ranking with the expected best 100, including stable ties and repeated submissions.
71: 
72: **Acceptance Scenarios**:
73: 
74: 1. **Given** a populated list, **When** two different qualifying results are saved simultaneously, **Then** both are considered against the latest saved scores, with only scores below the resulting cutoff removed.
75: 2. **Given** simultaneous equal scores, **When** saved, **Then** the first successfully saved result ranks ahead of later equal results, consistently on every device.
76: 3. **Given** a successful save, **When** the service restarts, **Then** the result remains unless legitimately displaced by higher-ranked results.
77: 4. **Given** excessive contention or unavailable storage, **When** a result cannot be confirmed within the deadline, **Then** an error replaces any success claim and the player can immediately play again.
78: 5. **Given** malformed scores or excessive submission traffic, **When** requests arrive, **Then** invalid results do not change the ranking and excessive submissions receive a clear temporary rejection.
79: 
80: ### User Story 5 - Keep playing when publication fails (Priority: P1)
81: 
82: If the service cannot be reached after Game Over, I want an error and my local personal best retained, without a pending score being submitted later.
83: 
84: **Why this priority**: The user explicitly chose no deferred score submission and no account requirement.
85: 
86: **Independent Test**: Finish offline, restore connectivity, then restart the app. Verify the personal best remains and the failed run is never submitted later.
87: 
88: **Acceptance Scenarios**:
89: 
90: 1. **Given** Game Over without connectivity, **When** qualification cannot be checked, **Then** no name is requested, the local best is preserved, and an error replaces any claim that the score did or did not qualify.
91: 2. **Given** a valid name and a failed submission, **When** the error appears, **Then** the local best remains and no automatic or deferred publication is queued.
92: 3. **Given** a failed run submission, **When** connectivity returns, a list is refreshed, or the app relaunches, **Then** that run is not submitted again.
93: 4. **Given** a save may have completed but its response was lost, **When** an error appears, **Then** it says publication could not be confirmed, rather than asserting the score was not saved.
94: 
95: ### Edge Cases
96: 
97: - Empty and partially filled lists contain only real entries, without invented rows.
98: - Game Over means loss of the last life. A rescue, single lost life, pause-menu restart, abandoned run or return to title does not publish a result.
99: - Use the run's final score, never the previously saved personal best or the next run's score.
100: - Equal scores have consecutive ranks ordered by successful save order. A full list never replaces an earlier equal cutoff score.
101: - Names need not be unique, and one person may hold multiple places; a name does not identify a run or person.
102: - A result can be displaced after successful submission. The initial view shows the saved snapshot; a later refresh explains displacement and shows the bottom instead of highlighting another same-name entry.
103: - Negative, excessively large or malformed scores are rejected. Valid-looking scores do not prove genuine gameplay.
104: - Cancelling a view during submission stops further UI transitions but cannot undo an already completed save.
105: 
106: ## Requirements *(mandatory)*
107: 
108: ### Functional Requirements
109: 
110: - **FR-001**: Maintain one shared, all-time list of the best 100 completed-run scores, retaining fewer entries until 100 qualifying results exist.
111: - **FR-002**: Rank by descending score, then first successful save for ties; show consecutive ranks starting at 1.
112: - **FR-003**: Persist the list independently of any individual device and service process lifetime.
113: - **FR-004**: Evaluate only the final score of a run reaching Game Over through loss of all lives, independently of the local personal best.
114: - **FR-005**: Check current qualification after Game Over without blocking Play Again or Return to Title. Fewer than 100 entries accepts any valid non-negative score; a full list requires beating its current cutoff.
115: - **FR-006**: Request a name only after a successful qualification check; allow cancellation without publication.
116: - **FR-007**: Accept a single-line name of 1–20 visible characters after trimming surrounding spaces; reject control characters and explain validation failures. Display names as plain text.
117: - **FR-008**: Explain before submission that the name and score are public and require an explicit submit action. No account, email or real name is required.
118: - **FR-009**: Re-evaluate qualification when saving. Concurrent submissions must not cause lost updates, duplicate run entries or more than 100 ranked entries.
119: - **FR-010**: Following a confirmed save, highlight that exact run and centre it vertically where content permits. Keep the whole highlighted row visible at list boundaries.
120: - **FR-011**: Following confirmed non-qualification, show the bottom with the lowest rank visible, retain the player's final score, and offer another game. Do not request a name.
121: - **FR-012**: Provide a title-screen Highscores action that opens the beginning of the list and can be closed at any time.
122: - **FR-013**: Load and refresh independently of gameplay startup. Starting, restarting and playing must remain possible without a working network connection.
123: - **FR-014**: Provide loading, empty, available and error states; end visible loading/submission waits within eight seconds. Reading the list can be retried explicitly.
124: - **FR-015**: Suppress obsolete results from earlier screens or runs so a late operation cannot navigate away from an active game or attach a score to the wrong run.
125: - **FR-016**: Reject invalid result data and limit excessive submissions. Identical repeated submissions for a currently ranked run retain one entry; changed data for that run is rejected.
126: - **FR-017**: On a failed qualification check or submission, show an error, preserve the local best, and perform no automatic, later or next-launch submission of that run. Describe a failed save with an unknown outcome as unconfirmed.

131: ### Key Entities *(include if feature involves data)*
132: 
133: - **Completed run**: A finished game's unique identity, immutable final score and level reached. It belongs to the current result flow, not a deferred-submission record.
134: - **Highscore entry**: A qualifying run's identity, public name, score and successful-save order. Rank is derived from its place in the list.
135: - **Highscore list snapshot**: Up to 100 ordered entries and information distinguishing the observed version and freshness. Successful submission returns the snapshot in which the result was evaluated.
136: - **Local personal best**: The existing device-local maximum score, independent of participation in the shared list and preserved during failures.

138: ## Success Criteria *(mandatory)*
139: 
140: ### Measurable Outcomes
141: 
142: - **SC-001**: Across 100 startup/restart attempts covering normal, delayed and unavailable services, every attempt can start without waiting for highscores; added start latency stays below 100 ms against the same-device baseline.
143: - **SC-002**: For controlled acceptance runs at ranks 1, 50 and 100, the exact submitted entry is highlighted and fully visible, centred for interior ranks. Every non-qualifying run shows the lowest rank without a name prompt.
144: - **SC-003**: After 100 concurrent valid submissions, the saved ranking exactly matches the best 100 successfully considered results, including earlier entries, with no duplicates or lost higher scores. Transient failures are reported, and equal scores preserve successful-save order.
145: - **SC-004**: In normal conditions, 95% of list loads and confirmed submissions become visible within two seconds over 100 attempts with a warm service and at most 100 ms network round-trip latency. All stalled attempts leave loading within eight seconds.
146: - **SC-005**: Across connection interruptions before qualification, before save and after save but before acknowledgement, every run preserves its local best and none is queued or resubmitted after reconnection or relaunch.
147: - **SC-006**: A successfully saved ranking remains identical after a service restart when no new results arrive; two installations observe the same ranking version.

149: ## Assumptions
150: 
151: - The user confirmed on 2026-09-26: **no login**, with scores reported by the app. Validation and submission limits reduce malformed traffic but do not verify gameplay or prevent determined cheating.
152: - The user confirmed on 2026-09-26: connection failure means an error and the local personal best only. There is **no offline queue or later submission**.
153: - The list ranks runs, not unique people. It is global and all-time, without seasons, country filters, prizes or cross-device personal profiles.
154: - First successfully saved wins equal-score ties. Names are non-unique and not editable after submission in this version.
155: - Existing scoring, three-life rules, looping levels, audio, intro and local best behaviour remain the game's basis.
156: - Network access is required only for fresh highscores, qualification and publication. Gameplay remains independent of the shared service.
157: - Moderation tools, verified replays, score archives and regional rankings require separate scope decisions.
158: - Hosting access and a deployed service address are dependencies for end-to-end release validation. User-specified backend constraints and storage recommendations appear separately in [technical-proposal.md](technical-proposal.md).
159: - [Constitution v1.0.0](../../.specify/memory/constitution.md), ratified 2026-09-26, governs this feature; the plan's current review and implementation tasks apply its principles. The implemented highscore feature supersedes the earlier product document's exclusion of public leaderboards and preserves the existing gameplay rules.
