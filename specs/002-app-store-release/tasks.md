# Tasks: App Store Release Preparation

**Input:** [spec.md](spec.md), [plan.md](plan.md), [research.md](research.md), [data-model.md](data-model.md), [contracts/](contracts/), [quickstart.md](quickstart.md).
**Governance:** constitution v1.0.0 and root AGENTS.md. Actual branch `main`; feature directory `002-app-store-release`.
**Scope:** executable remaining-work list, not evidence that work/tests/deployment/Connect changes have run. Every checkbox starts unchecked. Existing loading/music/highscore changes are retained and revalidated, not rebuilt merely because this feature is new.
**Tests:** explicitly required by FR-013–FR-016, FR-024–FR-026 and acceptance scenarios. Add meaningful boundary/race/regression tests before affected implementation; record intended failing results, then require green before integration. Never fabricate physical evidence.

## Path and execution conventions

Paths are repository-relative; named new files are intentional implementation targets. `docs/releases/app-store/<version>-<build>/` means the real version/build discovered before package creation, never a value uploaded literally. Before that identity is known, keep discovery/blockers in `docs/releases/app-store/preparation.md`; move/copy relevant evidence into the identified package without losing history. Private owner contact, legal documents, reports, device logs and archives stay outside Git; package files contain non-secret references/checksums.

Phases are ordered by executable dependencies. US2 and US1 both have P1 priority; US2 precedes final US1 media because screenshots need the finished product. Candidate archive/upload belongs to the US2 acceptance chain and also satisfies US3's build prerequisite; there is no circular wait for US3. US3 owns saving/selecting/readback, not a second upload. Setup records unavailable inputs rather than inventing them: only tasks needing those inputs block, while independent coding/copy work continues. All stories require the shared evidence conventions in Phase2.

`[P]` applies only to the explicitly listed peer tasks after their preceding prerequisites pass, with separate files/evidence outputs. It never permits simultaneous edits of shared files, independent cloud mutations, or bypassing a named dependency. No commit/push/deployment happens in task generation; implementation uses then-authorized operations and existing protections. Never invoke Submit for Review, external beta review, automatic/scheduled/public release.
