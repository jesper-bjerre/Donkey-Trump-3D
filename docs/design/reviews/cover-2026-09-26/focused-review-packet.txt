2: 
3: ## Core Principles
4: 
5: ### I. Native iPhone Play Comes First
6: 
7: The product MUST remain a native 3D arcade game with iPhone as its primary acceptance target.
8: Starting, restarting and playing installed game content MUST work without a backend connection.
9: Optional online features MUST load asynchronously, have finite user-visible deadlines, and leave
10: navigation usable while loading or failing. A late response MUST NOT interrupt a newer game or
11: change a different run's result. Network or storage work MUST NOT block the render loop or UI thread.
12: 
13: New or changed player-facing screens MUST work in landscape with safe areas, readable text and
14: reachable actions. Applicable menu/list controls MUST support VoiceOver and larger text. Changes
15: MUST preserve the existing Reduce Motion, sound and haptics settings unless the feature explicitly
16: changes their behaviour. These rules keep short play sessions usable on the baseline iPhone.
17: 
18: ### II. Simple Components and Explicit Ownership
19: 
20: Gameplay rules, scoring, collision logic and run transitions MUST remain testable independently of
21: SceneKit, SwiftUI and networking. Rendering presents simulation state; UI presents player actions
22: and results. Cross-thread state transfers MUST use snapshots or an explicit synchronization boundary;
23: new UI state MUST have a defined main-thread/main-actor owner.
24: 
25: The backend default is one small ASP.NET Core service in `src/backend`, using built-in platform
26: facilities and a separate test project when needed. Additional services, stores, frameworks or
27: architectural layers MUST have a feature-level justification explaining the requirement they solve
28: and why the existing structure is insufficient. Package versions and runtime baselines belong in
29: project files and feature plans, rather than being frozen permanently in this constitution.
30: 
31: Each state has a clear owner: the app owns local gameplay and its personal best; the backend owns
32: validation, ordering and persistence of shared rankings. Accepting a client-reported score MUST NOT
33: be described as proof of genuine gameplay. Simplicity does not remove these ownership boundaries.
34: 
35: ### III. Correct Shared Data and Bounded Failures
36: 
37: Shared read-modify-write state MUST use storage-enforced concurrency control that works across
38: multiple service instances. An in-process lock alone is insufficient. A conflict retry MUST read
39: current state and recompute the result; unconditional overwrite MUST NOT be a fallback. Duplicate
40: submissions MUST use a stable result identity, with the supported deduplication scope documented.
41: 
42: Remote operations MUST define deadlines, cancellation behaviour, retry conditions and finite retry
43: limits. A potentially committed write with a lost acknowledgement MUST be reported as unconfirmed;
44: retry behaviour MUST NOT imply that a failed response proves no save occurred. Missing, corrupt or
45: unavailable storage MUST NOT silently become an empty replacement. Tests MUST cover these distinctions
46: when shared persistence is introduced or changed.
47: 
48: Local personal-best data MUST survive remote failures. Cached results MUST be identifiable as stale
49: and MUST NOT establish fresh qualification or confirmed publication. For the agreed highscore v1,
50: a failed qualification or submission MUST NOT create an automatic, deferred or next-launch upload.
51: 
52: ### IV. Original Content and Deliberate Data Use
53: 
54: Game models, textures, animation and audio MUST remain original project material or have documented
55: permission compatible with their use. Copied Nintendo/Donkey Kong assets MUST NOT replace the
56: project's procedural characters or synthesized soundtrack. References to the original game's feel
57: are design inspiration, not authorization to copy its assets. Player copy MUST preserve the original
58: parody/no-affiliation description.
59: 
60: Public name/score publication MUST require an explicit player action and explain what is public.
61: Data collection and logs MUST be limited to the feature's documented purpose; diagnostics MUST NOT
62: record secrets, full submission bodies or player names. Storage credentials MUST stay out of the
63: app, repository and logs. Public service traffic MUST use HTTPS; local development exceptions MUST
64: remain isolated from release configuration. Azure-hosted storage access MUST use managed identity
65: with permissions scoped to the required data resources.
66: 
67: Privacy/help copy MUST match implemented data flows. A new account, analytics, advertising or
68: tracking capability MUST be an explicit product-scope change, never an incidental dependency.
69: 
70: ### V. Evidence Before Completion Claims
71: 
72: Changed gameplay rules, persistence, concurrency, retry and cancellation behaviour MUST have
73: repeatable checks for their observable outcomes and relevant failure cases. Use deterministic
74: inputs, clocks or service/storage substitutes where timing and randomness would hide defects.
75: Cross-component contracts MUST be checked at their boundaries; a test that only mirrors an
76: implementation detail is not sufficient evidence for the player's requirement.
77: 
78: Verification MUST be proportional to the change. Run the affected build/tests and relevant existing
79: regression checks; documentation-only edits need document validation, not an unrelated full build.
80: Device-dependent claims, including physical silent-switch behaviour, touch usability and sustained
81: performance, MUST be backed by checks on the relevant physical device before release acceptance.
82: A simulator pass MUST NOT be presented as physical-device evidence.

86: MUST NOT be reported as a passing feature. Historical results MUST retain their date/context rather

### FILE README.md
1: # Donkey Trump 3D
2: 
3: A native iPhone 3D remake of the [Donkey Trump](../Donkey-Trump) browser game, and the same political satire. You play Jumpman Løkke, climbing sloped red truss girders and ladders up a half-built **Trump Tower, Nuuk** to rescue Motzfeldt. Donkey Trump throws barrels stencilled `TARIFFS` down at you from the top. Every new game opens with the cutscene: Trump carries Motzfeldt to the top, then signs an **EXECUTIVE ORDER: ALL GIRDERS SLANTED**, and the girders tilt one by one.
4: 
5: Swift + SceneKit + SwiftUI. The iOS app has no third-party dependencies, accounts or tracking. It includes optional [global top-100 highscores](specs/001-global-highscores/spec.md) backed by a small [ASP.NET Core/Blob service](src/backend/README.md). Gameplay works independently of backend availability; a production HTTPS service URL must be configured before online use.
6: 
7: Cold startup shows the owner's [Donkey Trump cover](docs/design/images/DonkeyTrumpCover.png), fitted without cropping over a dark background, then proceeds directly to the game. The [cover record](docs/design/cover-art.md) preserves its source prompt and possible use alongside App Store gameplay captures.

29: 
30: Open Highscores from the title, or finish a run. A fresh qualifying result offers optional public-name entry; Submit publishes and centres/highlights that exact run. 43: ## What's "3D" about it
44: 
45: - **Rendering:** physically based materials, HDR with bloom, SSAO, vignette and chromatic fringe, and soft deferred shadows from a moonlit key light, with image-based lighting generated per level theme.
46: - **World:** a Greenland night. An animated aurora shader in the sky, reflected in an icy sea, plus low-poly procedural icebergs, snowy mountains, colourful Nuuk houses, a rotating tower crane with blinking beacons, falling snow, and a gold "TRUMP TOWER" sign on the roof.
47: - **Characters:** procedural caricatures with jointed rigs (walk, climb, jump, tumble, cheer, rage, wind-up/throw, signing, carrying).
48: - **Themes:** each of the three layouts has its own sky and aurora (green, violet, ember).
49: - **Cameras:** a follow camera in play, and cinematic cameras for the title orbit, the intro, the rescue (with depth of field) and game over.
50: - **Effects:** sparks on a hit, dust when girders land and when thrown barrels touch down, fire trails on barrels hurled straight at you, Greenland red-and-white confetti on a rescue, and floating score text.
51: - **Feel:** haptics, screen shake (off with Reduce Motion), and iOS 26 Liquid Glass UI.
52: 
53: ## Gameplay: a faithful port
54: 
55: The gameplay core in `src/DonkeyTrump3D/Core` is a direct Swift port of the web game's pure systems. It keeps the same 800×600 level coordinates, the same `level1–3.json` files and the same tuning:
56: 
57: - `Slope.swift` is the line-segment slope resolver.
58: - `Player.swift` covers movement, the short 44 px jump (it can never clear a floor gap), coyote time, jump cut and overlap-gated ladders.
59: - `Barrels.swift` handles rolling, dropping off girder ends, taking ladders, and direct throws aimed at the player.
60: - `Simulation.swift` handles hits, barrel-jump points, the rescue, and `GameSession` (lives, score, retry, endless levels).
61: - `Level.swift` holds the endless difficulty ramp: layouts repeat 1, 2, 3, 1, … and the barrels approach fair limits.
62: - `IntroTimeline.swift` is the executive-order cutscene choreography.
63: 
64: Scoring follows the web game: 3 lives, +100 per barrel jumped, +1000 per rescue, a hit retries the level and keeps the score, and game over restarts from level 1. The best score is stored on the device. The simulation runs at a fixed 120 Hz step on SceneKit's render loop (`App/GameEngine.swift`). Each retry gets fresh barrel randomness.
